## 3. 7-day risk model versus a simple 4-week seizure count

Source: `backend/reports/ai_evaluation.md`.

Held-out synthetic patients: 45 (train: 105). Rows = one weekly snapshot per patient over the last 10 weeks: test n=405 (77 positive).
Thresholds chosen on TRAIN only (Youden J): model 0.178, baseline 0.227.

| | ROC AUC | Brier (lower = better) | sensitivity | false-alarm rate |
|---|---|---|---|---|
| model risk-0.2.0 | 0.702 | 0.144 | 0.714 | 0.402 |
| baseline: seizures in last 4 weeks | 0.688 | 0.144 | 0.610 | 0.314 |

AUC difference model − baseline: +0.015, 95 % patient-bootstrap interval [-0.011, +0.038]; Brier difference +0.000.

**Does the model beat the baseline?** No — not demonstrably: the interval includes zero, so the difference may be noise. Both rank patients moderately well (AUC 0.70 vs 0.69) — the simple count already captures most of the signal. This is synthetic data generated with known rules; a model trained on it mostly recovers those rules. It proves the pipeline works, not that it is clinically valid.

## 5. Load test

Source: `load/RESULTS.md` (conditions included).

Conditions: one laptop (16 CPU threads, 31 GB RAM, Linux), full `docker compose` stack,
PostgreSQL 16.6, requests go through nginx TLS → FastAPI. Each iteration = one phone syncing
a batch of 5 queued entries (4 dose confirmations + 1 seizure); every sync also re-runs the alert
engine for that patient. Per-IP rate limit raised to 1,000,000/min for runs 1–3 because all
virtual phones share one IP. Fresh seeded database unless stated.

| run | setup | VUs / duration | median | p95 | p99 | max | throughput | failed |
|---|---|---|---|---|---|---|---|---|
| 1 | 1 uvicorn worker, full history loaded, 3 accounts (all writes on 3 patients) | 50 / 60 s | 2.64 s | 4.41 s | 4.75 s | 5.21 s | 17.2 req/s | 0 % |
| 2 | 4 workers, 120-day history window, same 3 accounts, DB NOT reset (hot patients kept growing) | 50 / 60 s | 1.18 s | 5.55 s | 8.28 s | 12.53 s | 26.4 req/s | 0 % |
| 3 | 4 workers, 120-day window, 50 accounts spread over 150 patients, fresh DB | 50 / 60 s | **410.55 ms** | **751.39 ms** | 906.97 ms | 1.21 s | 112.1 req/s | 0 % |
| 4 | as run 3 but DEFAULT rate limit (300/min per worker) | 10 / 20 s | — | — | — | — | 1327.8 req/s | 95.96 % (HTTP 429, by design) |

Run 3 is the realistic scenario and the number we report. Run 4 shows the rate limiter
rejecting a flood from one IP. Reproduce:

    docker compose down && docker volume rm epilipsy_dbdata
    LOADTEST_ACCOUNTS=1 RATE_LIMIT_PER_MINUTE=1000000 docker compose up -d --build --wait
    docker run --rm --network host -v ./load:/load grafana/k6:0.55.0 run /load/sync.js
    # afterwards reset again WITHOUT LOADTEST_ACCOUNTS so the demo data is clean

## What is NOT validated

- **Nothing is clinically validated.** All patients are synthetic; the classifier's text data is a placeholder.
- Every threshold, first-aid line, drug rule, the pregnancy age range and the risk bands are TODO-verify by a neurologist.
- The alert evaluation measures how well the engine finds patterns **we injected ourselves**; real deterioration is messier.
- The models' subgroup gaps reflect small synthetic samples, not real bias; real bias is unmeasured.
- Load figures come from one laptop, one run per configuration, not a production deployment.
- Legal items (INPDP authorization, consent wording, data-deletion scope vs hospital records, medical-device
  classification) are TODO-verify with counsel.
- Arabic and Darija wording is provisional, pending native-speaker review.
